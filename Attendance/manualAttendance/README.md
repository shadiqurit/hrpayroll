# Manual attendance application, approval and recording

Manual attendance uses the same company routing policy as leave:

| Applicant | Approval route |
| --- | --- |
| Ordinary employee | Optional RP recommendation → HOD OR Plant Head → HRD record |
| HOD | Plant Head OR Managing Director → HRD record |
| Plant Head | Managing Director → HRD record |

One final approver decides. The other final candidate is cancelled. RP approval
is a recommendation; it does not finalize attendance. Rejection closes all open
steps. Final approval applies the corrected times immediately, then HRD records
the decision without approving or applying it again. MD applications stop until
a higher authority is configured, as in leave. Shared RP/final roles collapse to
one final action; the same person can subsequently perform a separate HRD record.

Routing reads the same `EMP_RP`, active `HOD`, and company `V_LEAVE_ROLES` used by
leave. Keep `PLANT_HEAD`, `MANAGING_DIRECTOR`, and `LEAVE_RECORD` role codes;
`LEAVE_RECORD` also identifies manual attendance's HRD recorder. No employee IDs
are hard-coded. Numeric actors are `EMPLOYEES.ID` (`:USER_ID`), not character
employee/IPI codes. `:G_COM_ID` and `:USER_ID` must be trusted, protected application
session items initialized from the authenticated user. Never accept actor IDs
from editable form items.

## Install

Use a clean SQL*Plus/SQLcl session connected as HRMS in a test database first.
Pause manual attendance writes until installation and APEX wiring are complete.
Install the machine foundation if it is not installed already:

```sql
@Attendance/00_install_machine.sql
@Attendance/manualAttendance/INSTALL_MANUAL_APPROVAL.sql
@Attendance/manualAttendance/CHECK_MANUAL_APPROVAL.sql
```

`MANUAL_ATT`, `M_ATT_APP_HISTORY`, `ATTENDANCE_DETAILS`, `EMPLOYEES`, `V_EMP`,
`EMP_RP`, `HOD`, `V_LEAVE_ROLES`, and machine foundation dependencies must exist.
For a new schema only, create the two manual tables from their export scripts
before the installer. Do not recreate tables in an existing database. DDL commits;
the installer creates/replaces objects and adds stage/version columns, but does
not run attendance rebuilding or make approval decisions. It replaces MAX+1 key
triggers with sequences and removes the old insert-routing trigger. It updates
`P_ATT_UPDATE_DETAILS` with an optional trailing `p_emp_id`; existing callers keep
their current behavior. Recompile existing dependent procedures/packages if your
database reports them invalid after this replacement.

Existing requests/history remain intact with `WORKFLOW_VERSION = 0`. They are
visible in reports with an administrator-review indicator, excluded from the new
action inbox, and cannot be acted on through the new package. Review old pending
requests and resolve/archive them under administrator control before creating
replacement requests; do not delete approval evidence or reset approved requests
to draft. Legacy drafts without history can be deleted by their applicant and
recreated. No guessed route migration runs. A rebuild refuses ranges containing
legacy approved corrections so their attendance is not silently lost.

## Where status and pending requests appear

- **Page 410 — Manual Attendance Register:** use `apex_applicant_report.sql`
  for the My Manual Attendance region. Show `STATUS_TEXT`,
  `PENDING_WITH`, and `RECORDING_STATUS`. Drafts appear even with no history.
- **Page 410 — Pending Manual Attendance region:** use `apex_pending_inbox.sql`. RP/final candidates
  see their currently actionable requests. HRD sees final-approved requests to record.
- **Page 410 — Recorded Manual Attendance region:** use `apex_recorded_report.sql` for HRD's completed work.
- **Page 411 — Manual Attendance Entry and Detail:** use `apex_request_detail.sql` and
  `apex_request_history.sql`; the selected request ID is `P411_ID`.
- **Page 418 — Manual Attendance Approval:** use `apex_approval_detail.sql` and
  `apex_approval_history.sql`; the selected request ID is `P418_ID`.

The register queries include `REQUEST_URL`, generated by `APEX_PAGE.GET_URL`
for Page 411 (applicant requests) or Page 418 (approval/HRD requests), with the
target page cache cleared and its request key set. Use it as the report link
target. See [APEX_PAGES_410_411_418.md](APEX_PAGES_410_411_418.md) for exact page items,
process conditions, buttons and navigation.

`V_M_ATT_REPORT` has one row per application. `V_M_ATT_APPROVAL` has one row per
saved approval candidate; use it for inbox/history, not the applicant list.
Names and roles in `PENDING_WITH` come from the saved history. Missing person
names fall back to numeric IDs. Example progression:

| Action | STATUS_TEXT | PENDING_WITH | RECORDING_STATUS |
| --- | --- | --- | --- |
| Save draft | Draft | empty | Awaiting approval |
| Submit | Pending with Name (Reporting Person) | RP name | Awaiting approval |
| RP recommends | Pending with Name (Head of Department), Name (Plant Head) | Eligible alternatives | Awaiting approval |
| One final approval | Approved | HRD name | Pending HRD recording |
| HRD records | Approved | empty | Recorded |
| Reject | Rejected | empty | Not required |

Raw request codes are `D` draft, `F` forwarded, `A` approved, `R` rejected.
`REQUEST_STATUS` is `D`, `F`, or `A` (rejection retains `F`, as in leave).
History uses `WAITING`, `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED`, `RECORDED`.
Only `PENDING` is actionable. Approval group numbers are RP=10, alternatives=20,
HRD=50. The package checks the saved route against current assignments on each
action; changed company/roles or malformed histories stop for review.

## APEX request form

Register is Page **410**, Entry/Detail is Page **411**, and Approval is Page **418**.
No APEX application/page
export is in this repository, so these are ready-to-wire page sources, not an
automatic modification of a deployed application. All supplied entry SQL
uses `P411_` item names. Approval/detail/HRD SQL uses `P418_` item names.

1. Use request key `P411_ID`; fields `P411_ATT_DATE`, `P411_M_INTIME`,
   `P411_M_OUTTIME`, `P411_REASON`, `P411_COMMENTS`. Use date mask `YYYY-MM-DD` and
   punch mask `YYYY-MM-DD HH24:MI`. Punch fields contain full dates, including the
   following date for an overnight OUT. ATT_DATE is the shift date; an OUT-only
   overnight correction must explicitly retain the previous shift date.
2. Fetch existing records through the authorized detail query. On a create link,
   clear page cache/ID. Show raw employee/company/status fields as read-only.
   Permit editing only for the applicant's new-workflow draft. Submitted,
   rejected, approved and recorded requests are read-only.
3. Disable the old Automatic Row Processing/history DML and every old routing or
   `FORWARD_ATTENDANCE_APPROVAL` process. Its retained legacy signature now raises
   an explicit migration error; it cannot silently use the old ambiguous actions.
4. Create one After Submit process from `apex_save_submit.sql`, conditioned on
   requests `CREATE,APPLY,SAVE,FORWARD,SAVE_DRAFT`. Clear any old FORWARD-only
   condition. Like leave, Create/Apply/Save/Forward **save and submit**; use a
   distinct **Save Draft** button (`SAVE_DRAFT`) when no submission is intended.
5. Add `DELETE_MANUAL` using `apex_delete_draft.sql` with validations disabled.
   Exclude it from save/submit. The package permits only the applicant's draft
   without history. Exclude Cancel and approval buttons from save/submit too.
6. Branch to Page 410 only on success, clearing Page 411's form cache. Let
   APEX commit successful requests; the package never commits internally. The
   combined save/submit process rolls back its own save if routing fails.

Require a reason and at least one corrected time. At submission the package
serializes on the employee and rejects another pending/approved correction for
that shift date. Rejected applications permit a fresh application. Drafts can
coexist until one is submitted. Submitted request content is protected by a
database trigger as well as page settings.

## APEX approval form

On Page 418, link inbox `ID` to `P418_ID` (and `DID` to `P418_DID` only if the form requires
it). Keep request and history fields read-only; the package locates the actor's
pending assignment itself. Use `apex_approval_detail.sql` and `apex_approval_history.sql`.

Use action item `P418_ACTION` with static LOV display/return pairs
`Approve;APPROVE` and `Reject;REJECT`, and optional `P418_ACTION_COMMENTS`
(maximum 300 bytes). After Submit, When Button Pressed = `SUBMIT`, run
`apex_approval_action.sql` only. Show the action/select/button when the current
actor has a `PENDING` RP/HOD/Plant Head/MD step and parent status/stage `F/F`.
The package repeats all checks under a request lock, so stale links and racing
final candidates cannot approve twice.

HRD uses a separate `RECORD` button and `apex_record_action.sql`, with parent
`A/A` and a `PENDING` `LEAVE_RECORD` step assigned to the current user/company.
Hide the approval LOV/Submit for that step. HRD cannot reject or approve the
request and cannot record before final approval. After success return to and
refresh the inbox (and applicant report if displayed on the same page).

## Applying and retaining corrected attendance

Final approval requires exactly one existing `ATTENDANCE_DETAILS` row for that
employee/company/shift date. Generate its roster/schedule first. Missing or
duplicate rows, or conflicting effective IN/OUT times, roll back the approval,
history and attendance changes together. No arbitrary schedule row is fabricated.

Non-null approved times override the corresponding stored machine/derived
boundary; an omitted boundary retains the existing value. The resulting pair
must be ordered and span no more than 24 hours. The existing metric procedure
recalculates only the applicant/date with `p_commit => 0`; holiday/weekend rules
remain those of attendance. RP, rejection and HRD recording do not post times.
`POST_MANUAL_ATTENDANCE` can safely replay the final decision without adding rows.

For scheduled/historical machine-plus-manual rebuilding, wire the scheduler/call
site to the new entry point:

```sql
BEGIN
    HRMS.p_att_rebuild_manual(DATE '2026-11-01', DATE '2026-11-10', p_commit => 0);
END;
/
-- Review, then COMMIT or ROLLBACK in this session.
```

It refreshes the requested inclusive range plus neighboring days, derives
continuous machine shifts, replays approved manual boundaries with explicit
manual priority, then calculates metrics. It locks affected forwarded/approved
requests so an approval cannot be overwritten concurrently. Replace existing
machine-only daily calls with this wrapper when deploying manual approval;
running only `P_ATT_SCHEDULE`/`P_ATT_REBUILD_MACHINE` afterwards can overwrite a
manual correction. Scheduler definitions were not supplied and are not changed
by the installer. This wrapper covers machine and manual data; full-day and
short-leave attendance replay still require their separate agreed rules from
the main Attendance README. Do not run it on dates with those adjustments until
that integration exists.

## Verification

Run `node Attendance/manualAttendance/tests/approval_queries.cjs` for offline
checks of actual workflow SQL/report/inbox sources, and
`node Attendance/tests/machine_rebuild.cjs` for existing attendance regressions.
Run `TEST_MANUAL_APPROVAL.sql` in a test HRMS database for PL/SQL execution,
approval/posting/rollback checks. It consumes sequence numbers but rolls back
business data. Offline SQLite checks do not compile Oracle PL/SQL or prove
Oracle locking/transaction behavior. Check concurrent final candidates in two
Oracle sessions before deployment: the second action must wait then fail after
the first commits. Check a concurrent rebuild/final approval too. Existing
configuration changes during an open route deliberately require administrator
review rather than silently rerouting it.
